# Developing GamePlayer

Needs Visual Studio Build Tools 2022 with the C++ workload (MSVC, Windows SDK, and the bundled CMake and Ninja). Nothing has to be on PATH; the scripts find the tools themselves.

## Build

    build.bat

Configures with CMake (Ninja, MSVC, RelWithDebInfo) and builds everything into `build\`. The app is `build\GamePlayer.exe`, a single executable with the C runtime linked in.

## Run the unit tests

    test.bat

Builds the test program and runs it (`build\gameplayer_tests.exe`, doctest). It exits non-zero if a test fails.

## Run

    build\GamePlayer.exe

F11 toggles borderless fullscreen; Esc leaves it. Up / Down change the volume, M mutes, J / K move the sound 50 ms earlier / later (Audio Delay, 0-500 ms); each shows a short line centred at the top for 1.5 s (a held key at a limit repeats nothing on screen; only the time restarts). F (or View > FPS counter) toggles the FPS counter top-left (with Frame Generation off, the presented rate, e.g. "30 FPS": the Game Rate on Auto, the Frame rate override's rate otherwise; blank for the first two seconds after a start or Feed restart, until the rate window is full; hidden while a state message such as Loading or No signal shows; the Signal Rate is in Help > About and the log; off on a fresh install, then remembered; drawn only into frames presented anyway, so it never adds a present and freezes on a still picture). `--rate auto|30|60` sets the Game Rate override, `--tolerance X` the near-duplicate tolerance (e.g. 0.005, at most 0.05), for one run (neither is saved). Once a second the log has a `Frames:` line: arrived, unique, repeats caught exactly and by the tolerance, presented, dropped, the Game Rate (detected), presented rate and Signal Rate, the largest near-repeat share and the closest Unique Frames (under 1% of words differing: a sign repeats are not bit-identical), the compare time before and after presenting, and the FPS counter text (or `warming up`, `off`). With Frame Generation running the counter has two equally sized lines, `Game 30` and `Shown 120`. During generation Game measures successful real endpoint presents (a superseded or failed endpoint is excluded), while off-mode retains the existing Processor-emitted rate. Shown measures all successful DXGI presents, including Generated Frames and repaints, over the last two seconds without a monitor cap. Starting, failed and unavailable generation retain the one-line counter. Help > About labels the override rate `Game:` during generation and shows measured total presents as `Shown:`; with generation off it keeps the old `Shown:` override line. It also reports the actual Generation Factor (or off, with the availability/startup reason), plus actual Sharp Upscale usage and Feed -> shown sizes. Driver failure and 4x fallback reasons reach About through a typed, owned notification mailbox; stale requests are discarded and no window message owns a raw pointer. The Presenter publishes these actual states under its statistics mutex; the FPS counter still never wakes it. Only one copy runs: while one is open, starting another just brings it forward (so a smoke run does nothing while the user's copy is open).

The menu bar (windowed only, hidden in fullscreen) overrides the automatic choices: Capture Card, Resolution, Frame rate, the audio values, Fullscreen, Always on top, V-sync (off by default), FPS counter. Two Capture Cards of the same name are numbered and told apart by their identifier. A chosen resolution that does not start, or that the card does not offer, gives way to the default mode for that run, with a short line saying so. Each choice logs a `Menu:` line; `Menu: open` / `closed` bracket an open menu.

Remembered settings (ticket 09): the menu choices, volume, mute, Audio Delay and the windowed position, size and maximised state are kept in `%APPDATA%\GamePlayer\settings.ini` (key=value, `version=1`; delete it for the defaults), and the FPS counter. Never fullscreen: the app always opens windowed, at the position it had before fullscreen. Saved about two seconds after a change settles and at exit, through a temporary file renamed over the old one. Anything missing or invalid is the default for that value; the window reopens at the size it had (a snapped one too, with black bars); a remembered position not fully on a connected monitor gives the default size on the primary monitor, not maximised. A save that fails is tried again after 30 s, on the next change, and at exit. The Capture Card is found by its symbolic link, then its name, else the automatic choice (the preference is kept). `--settings PATH` uses another file: smoke runs should, so the user's own file is left alone. The log has `Settings:` lines (what was loaded, each save) and `Window: remembered position ...`.

`--run N` closes the app by itself after N seconds, for unattended smoke runs. Each run rewrites `GamePlayer.log` beside the executable: the capture devices found, every mode the card offers, the chosen device and mode, the colour range and matrix read from that mode, then frame counts and the arrival-to-present time (once a second for ten seconds, then once a minute). For sound: every audio capture endpoint, the chosen one, both endpoints' formats, periods and buffers, the buffer target, then (same rhythm) the fill, drift correction rate, underruns and overruns. Video Area: every state change (`Video Area: Loading -> Playing`), and once a second a `Signal:` line with every value no-signal detection could use (frames, stream ticks, type changes, discontinuities, luma of the latest frame, sound frames, silent frames, peak). Retries log their details only when the device list changed. Each audio key logs the new volume, mute, Audio Delay and buffer target.

Press G or choose View > Frame generation to cycle through off, 2x, 4x and Target. The line says `Frame generation Target (144)` with the rate in use. The settings file remembers the choice as `frameGeneration=off`, `2x`, `4x` or `target`. Missing and unrecognised values select off. V-sync is unavailable while generating. With generation off, the Lossless Scaling present rules below apply.

Target (ADR 0004) shows one frame per refresh of the monitor the window is on, with V-sync on and no tearing (or fewer: View > Target rate, below). With Target rate Monitor the rate in use is that monitor's refresh (`EnumDisplaySettings`), read again once a second, so it follows the window to another monitor. The V-sync item shows on and greyed out in Target; the user's own setting is not changed or saved and applies again after Target. Target runs the 4x generator (the 2x frames if the second FRC failed; Target stays on). The Presenter then skips the timed sequences: it waits on the swap chain's waitable object (once per vsync, max frame latency 1) and presents with sync interval 1 every time. A new Unique Frame is converted and generated as soon as it arrives, not at the vsync. For each vsync the pure `TargetSchedule` picks the ladder frame (first quarter, middle, last quarter, the Unique Frame) nearest in time to that vsync's display time, or none (the previous frame again). The ladder's times are those 4x would use: the first frame due when the ladder is ready, plus one refresh (a present is displayed at the next vblank), the others a quarter interval apart, but no later than a slot (the time between presents) and half a step after the Unique Frame arrived (`LadderStartTicks`): the presents made until the next Unique Frame is taken are displayed over one interval from a slot after the arrival, so each then falls on its own ladder frame. It never goes backwards and never shows an older Unique Frame's frames after a newer one began. It never drops a real frame (Q17): a 60 fps game on 144 Hz gets 2.4 presents per Unique Frame for 4 ladder frames, so nearest-in-time alone passed over the Unique Frame itself about half the time (seen: 25-35 a second not shown, the Game counter at about 33); the present displayed from the time the next Unique Frame is due (its arrival an interval later, less a sixteenth of a step for arrival jitter) shows the Unique Frame itself. Modelled in `target_schedule_test.cpp` (60 fps on 144, 120 and 72; arrival jitter 0.3 ms): none not shown, Unique Frame on screen about 19.5 ms after arrival (before: 21.9 ms when shown), up to one repeat in five Unique Frames at the worst phases. When the rate in use is not above the Game Rate, real frames only. The vblank times come from `IDXGISwapChain::GetFrameStatistics` after each present (`VsyncClock`). The vblank period is measured over 64 vblanks or more, else the monitor's nominal one. Missed vsyncs are the vblanks that showed no new present; with real frames only (no presents between new frames) they are the presents first shown after the vblank they were made for (`VsyncClock::Late`, judged by time: on the 59 Hz second monitor the refresh counts lag and jump, and counting vblanks there read 0 to 419 a second). Seen on the user's PC: borderless/windowed, 144 presents per second, 0 missed, period 6.946 ms. On the 59 Hz second monitor the swap chain still accepted 144 presents per second and its statistics report 144 Hz vblanks, so Target follows that measured cadence. Once a second the log has a `Target:` line: the rate in use, vsyncs, presents, Generated Frames and Unique Frames shown new, repeats, missed vsyncs, ladder (`x8`, `x4`, `x2`, `real frames only`; `none` before the first ladder; the Unique Frame after a start or pause has none and changes neither this nor real frames only) with the depth in use (x8 only when wanted and the generator can make eighths) and the Game Rate it is chosen from, Unique Frames (and how many never had their own picture shown), the period (measured or nominal), the worst generation time, and where the vsync times came from (`wake-up time (no frame statistics this second)` when no present was made, with the error only when a call failed). At a forced 30 fps it reads about 144 vsyncs and presents, 90 Generated, 30 Unique, 24 repeats. The arrival-to-present time in the `Stats:` line is about 29 ms (4x: about 25 ms). The FPS counter keeps its two lines: Shown is all presents (about 144), Game the Unique Frames shown, so the Game Rate (every one is shown).

View > Target rate (ticket 03) picks the Target Rate: Monitor (the default, labelled with the refresh of the monitor the window is on, e.g. "Monitor (144)"), 120, 72, 60, and Custom. Each choice logs `Menu: Target rate ...` and shows `Target rate N` with the rate in use. Saved as `target_rate=monitor` or the number; a missing, unreadable or out-of-range value (outside 1..1000) means Monitor.

Custom (ticket 04) opens the first modal box of the app (`platform/target_rate_box.*`, plain Win32, a dialog template built in memory, no resource file): title "Target rate", one number field pre-filled with the custom number, else the rate in use (`CustomBoxStart`), OK and Cancel; Enter accepts, Esc cancels. `TargetRateTyped` (`core/target_rate.h`) accepts whole numbers 1 to 1000 only (spaces around ignored); anything else (0, 1001, letters, empty, decimals, signs) disables OK and shows "1 to 1000"; Enter then does nothing. After OK the number is the Target Rate (the rules above: rate in use, uneven notice, real frames only) and the custom one: the menu shows "Custom (100)", checked, and keeps that label when a preset or Monitor is picked later ("Custom…" until a number is typed; a preset typed in the box checks the preset). Saved as `target_rate_custom=N` or `none`; out of range or unreadable means none. A saved `target_rate` that is no preset is also the custom one, so a file from before keeps it; a bad saved one means Monitor. Logs `Menu: Target rate Custom box open (shows N)`, `... cancelled`, and at launch `Menu: Target rate Custom kept N`. The box is owned by the window, so it shows above it in fullscreen without leaving fullscreen (Esc in the box closes only the box); the Feed keeps playing behind it (the Presenter has its own thread, the box pumps the window's messages). The menu bar is hidden in fullscreen, so there the box only opens by a `WM_COMMAND` (`kMenuTargetCustom`), as the smoke run does. A quit while it is open (`--run`, sign-out) closes it as Cancel. 2x and 4x ignore it. The rate in use is the smaller of the Target Rate and the refresh (`core/target_rate.h`, Q16): the user's number is kept as chosen, and on a faster monitor a higher one works. Below the refresh, `PresentPacer` spreads the presents over the vsyncs as evenly as possible (Bresenham): each present's sync interval is the floor or the ceiling of refresh / rate (72 on 144: 2 every time; 120: four of 1 then one of 2; 60: 2, 2, 3, 2, 3), at most 4 (a longer span adds presents of the same picture, for ticket 04's low rates). The schedule then picks the ladder frame for that present's display time (the next vblank plus the extra vblanks it waits). A rate that does not divide the refresh shows the notice "120 on a 144 Hz monitor: motion will not be perfectly even" for 4 s at the top, as a smaller second line under the feedback line (`ShownTexts::ShowNotice`: the two came together and overwrote each other), alone once the feedback ends, once when it starts applying (chosen, Target turned on, or the window moved to a monitor with another refresh), logged as `Target: notice`. If the rate in use is not above the Game Rate (Q17, with a 10% margin for arrival jitter, so 60 at a 60 fps Game Rate qualifies; one rule, `RealFramesOnly`, applied per Unique Frame by `TargetSchedule::Begin`; a Unique Frame with no interval, after a start or pause, keeps the answer before), only real frames are shown, and the pacing stops: each new Unique Frame is presented at the next vsync, nothing between (a text or a resize presents too), so no real frame is dropped by the pacing. Seen on the user's PC: with presents only for new frames the frame statistics count fewer vblanks than passed (period read as 7.27 ms on 144 Hz), so `VsyncClock` starts over whenever presenting switches between real frames only and generating. The `Target:` line now reads `rate 72 of 144 Hz`, counts the vsyncs the presents cover and `held` (vblanks held on purpose by a sync interval over 1), and subtracts those from the missed vsyncs (with real frames only: late presents, `(late presents)`).

`platform/amf_generator.cpp` loads the AMD driver's AMF runtime from the Windows system directory. A worker creates FRC on the Presenter's Direct3D 11 device at the Feed size. It holds its own device reference until setup finishes, so the Presenter can show real frames, switch off, rebuild or stop during setup. FRC uses interpolated-only mode, the SUPER profile with native motion search, fallback blending and no future frame. SUPER, not HIGH: Veyra-NRVideo found HIGH loses fast camera pans on 1080p console capture and blends (double image), SUPER tracks them for about 0.3 ms more GPU per call (their RX 9070 XT); watch x8's missed vsyncs. The Presenter copies each BGRA input into a four-texture ring. After submitting N it polls for about 2 ms, discarding outputs whose timestamp differs from N. A matching intermediate frame precedes N by half the Unique Frame interval. When none is ready, N is shown alone. The Presenter draws its texts after generation. A runtime failure disables generation for the session and preserves the saved choice. During asynchronous startup the Presenter retains the latest real BGRA picture in its own texture, then primes both stages from that picture on the first ready call. The worker never uses the immediate context for this priming. Its driver setup (`InitDX11`, FRC `Init`) does run on the shared device with multithread protection on; that makes each context call safe but does not keep a Presenter pass whole, so a driver that changes context state during setup could disturb one frame. Not seen so far. A size/device change still needs new asynchronous driver setup: its completion time is unbounded, so the ticket 03 two-Unique-Frame target cannot be guaranteed across such a change. Once setup is ready and the incoming interval is suitable, the retained previous picture permits 4x on that first ready call instead of wasting another input. A pause/restart with an existing ready session still re-primes within two Unique Frames. Startup logs report elapsed setup time, real input count and the first ready output count.

The x8 ladder (Target only, ticket 02). When the Game Rate is low for the rate in use, Target asks for seven Generated Frames per Unique Frame instead of three: the eighths 1/8, 3/8, 5/8, 7/8 between the quarters. The pure `LadderDepth` (`core/ladder_depth.h`) chooses x4 or x8 per Unique Frame from the Game Rate over about the last second (at least half a second measured; until then, and after `Reset` when generation stops, x4) and the time between presents at the rate in use (the measured refresh, or longer below it): x8 above 2.8 presents per Unique Frame, x4 below 2.5 (Target 72 at 30 fps: 2.4, x4), in between it keeps what it had (at 144: about 51 fps and below x8, 58 and above x4). The gap before a Unique Frame the arrival rules forgot the earlier for (a pause, a hitch, a Feed restart) is not one of the measured intervals, so a short hitch changes neither the Game Rate nor the depth (seen before: three hitches of about 250 ms read Game Rate 0.0); a pause over a second keeps the depth and measures again. The Presenter passes it as `FrameGenerator::Input::eighths`; 2x and 4x never set it. In Target (with the second FRC) `MakeAmfGenerator(four, onFailure, eighths=true)` also starts a third FRC on the worker; it is fed only while x8 is wanted, with the quarter stream (first quarter, middle, last quarter, N; sequence numbers N x 4 - 3 ... N x 4, eight input copies). Same rules as the second stage (`ThirdStageStep`): an output is used only with the number just submitted; if it was idle, N's quarters are missing, or the earlier frame was forgotten, its history is flushed and restarts at N, and that Unique Frame uses x4. All or fall back (`ReadyLadderFrames`): seven only with all four eighths, else the quarters' count; never a partial x8. `Generated(i)` with seven: eighths at even places, Q1, M, Q3 at 1, 3, 5. If the third FRC cannot be created or fails, the generator logs `FrameGen: third FRC unavailable (reason), Target uses the x4 ladder`, Target stays on x4 and the window shows `Frame generation Target (x4 ladder only)` once (`GenerationOutcome::FallbackToQuadruple`; the reason goes to the log only, not About); the next generator in the session is made without a third FRC. A second-stage failure also ends x8. Generation runs on the presenting thread and x8's seven FRC calls take about 5.3 ms. Taken at once (as x4 does), they often straddled a vblank (6-18 missed vsyncs a second). So while the depth in use is x8 (wanted, and `FrameGenerator::MakesEighths`: not after the third FRC failed or on 2x frames) a new Unique Frame waits in the slot for the vsync: that pass presents first, then takes, converts and generates, which fits before the next vblank. Its ladder would then end after the next Unique Frame is taken, and the Unique Frame's own picture would almost never be shown: `LadderStartTicks` starts an x8 ladder at most a refresh and 1.25 eighths after the Unique Frame's arrival (30 fps at 144: about 12.1 ms), counted from the arrival so the steps stay evenly spaced from ladder to ladder; the Unique Frame is then shown at the latest at the vsync that takes the next one; a ladder's first eighth may be passed over. x4 and 2x, taken at once, have their own cap (a slot and half a step, above). The `Target:` line adds `(depth x8, Game Rate 30.0)`; a `Target: ladder depth x8 (...)` line logs each change. `FrameGen:` adds `eighth frames N (x8 wanted, made, x8 CPU average / worst)`, the time of the Unique Frames that got the whole x8 ladder. Seen on the user's PC at a forced 30 (60 s each): 720p and 1080p alike, 210 Generated Frames made per second, 144 presents, 0 missed vsyncs, 108-111 Generated and 30 Unique Frames shown, 3-7 repeats, at most 1 Unique Frame not shown per minute; x8 generation CPU 5.3 ms average (720p 5.31, 1080p 5.26), worst second 8.9 / 9.7 ms; arrival-to-present about 33-34 ms (x4: about 29). At a forced 60: x4, never x8, one depth line per run at 30 (no flipping).

At 4x a second FRC processes the doubled stream. It receives the middle frame and then real frame N, each with its own timestamp. Both matching quarter frames must arrive to show first quarter, middle, last quarter and N, each a quarter interval apart. A missing quarter leaves only the middle and N. After missing a middle or a discontinuity, the second FRC starts its history at N. A second-stage failure leaves 2x running and updates the feedback and menu. The Viewer applies no monitor refresh cap.

`FrameGen:` logs the start result and, during playback, the factor, Generated Frames made, Unique Frame intervals attempted, quarter frames used, successful presents, discarded late outputs, and average and worst generation time per attempt on the presenting thread. GPU time is unmeasured.

The explicit `60 fps (every frame)` override deliberately passes Repeated Frames to the Presenter and FRC too, preserving the existing user choice. Frame Generation follows that real-input cadence; Auto remains the mode that drops Repeated Frames before generating. This override is covered by the Processor tests and does not silently turn back into Auto.

The developer-only command-line switch `--frames-per-unique 2` or `--frames-per-unique 4` repeats each picture at equal intervals. The presenting thread asks the GPU-side `FrameGenerator` for intermediate pictures and draws the overlays onto each output. The pure `FrameSchedule` uses the last two Unique Frame arrival times for spacing and anchors all deadlines to the first present. A high-resolution waitable timer wakes the presenting thread. Text, resize and menu wake-ups recheck the same deadline. A new arrival supersedes an unfinished sequence. Starts, Feed restarts, device rebuilds, picture-size changes and unsuitable arrival intervals show one frame immediately. During timed sequences the Presenter uses unsynchronised presents. The once-per-second `Timed frames` log counts Unique Frames, successful presents, early drops and late skips, and records the worst lateness and Present call duration. The switch is never saved.

## Sharp Upscale

Press U or select View > Sharp upscale to step the remembered choice (off on first use; the steps are below).
Every actual step logs `Menu: Sharp upscale off|FSR 1|AMD VideoSR`, even at native size where FSR 1 is unused.
For an enlarged Feed the Presenter runs FSR 1 EASU directly from each finished picture
to a texture matching the fitted picture rectangle. RCAS sharpens that texture pixel for
pixel at 0.2 stops below maximum. Both passes use the same display-encoded RGB as the
plain stretch. Generated Frames follow the same path and the text overlay is drawn last.
A picture shown at exactly its own size (1080p in fullscreen on a 1080p monitor, or 720p in the default 1280x720 window) gets RCAS alone, straight from the picture, pixel for pixel (`UseNativeSharpen`): capture cards soften the picture a little. Logs `Upscale: RCAS sharpening at native size on/off`; Help > About says `sharpening only`. Smaller pictures use the smooth path. The optional D3D11 shaders require
no AMF runtime. An `Upscale: FSR 1 on/off` transition (EASU actually drawing, so off while VideoSR scales) logs the Feed and shown sizes.
Compilation or resource failure logs the reason and falls back to smooth stretching.

With an AMD runtime, U steps off, FSR 1, AMD VideoSR, off (`ToggleSharpUpscale`; saved as `upscaler=fsr1|videosr`, only with `sharpUpscale=true`; the line says `Sharp upscale FSR 1` / `AMD VideoSR`). VideoSR (`platform/amf_upscaler.*`, idea from Veyra-NRVideo) is AMF's HQScaler component from the AMD driver, VIDEOSR1_1 (1.0 if the driver does not keep 1.1), on the Presenter's D3D11 device. It replaces EASU only: Feed-size BGRA in, the fitted size out, then the Show pass (Night mode), no RCAS (VideoSR sharpens itself). Native size still gets RCAS. The HQScaler names are written in `amf_upscaler.cpp` from the SDK's documentation; its header is not vendored. Each session (device, input size, output size) starts on a worker after the size has held 300 ms; until ready, when a picture is not back within 4 ms, and for the run after a failure, FSR 1 is used (`Scale` may clear the context state either way; the Presenter rebinds after every call). Logs `Upscale: AMD VideoSR 1.1 ready in N ms`, `on/off`, and once a second `scaled N, not ready N, CPU average / worst`. Help > About says `on, AMD VideoSR 1.1 (...)` or `on, FSR 1 (...)`. Seen on the user's PC (RX 9070, 720p to 1758x989, Target 144): ready in 250 ms, 144 scaled a second, CPU 0.25 ms average, 0.5 ms worst, no missed vsyncs added. Picture quality against FSR 1: the user's eyes.

## GPU priority

After creating the device the Presenter raises the process's GPU scheduling class to High (`platform/gpu_priority.*`, `D3DKMTSetProcessSchedulingPriorityClass` from gdi32, own process only, idea from Veyra-NRVideo). Logs `GPU priority: High (class 2 -> 4, ...)` or why not. Nothing to undo at exit.

## Night mode

Press N or select View > Night mode to step through off, low, high and auto (remembered as `night_mode=off|low|high|auto`; missing or unknown means off). It lifts the dark parts of the picture so night scenes read better; anything with a peak above 0.65 (display-encoded) is left exactly as it was, and black stays black. The curve (`platform/night_mode_shader.h`, strength 0 / 0.45 / 1 from `core/night_mode.h`) is prepended to every Presenter shader and called only by the last pass that writes the picture (Show, or RCAS with Sharp Upscale), so real and Generated Frames get the same look while Frame Generation's inputs stay untouched; the text overlay is drawn after it. The strength (0 to 1) is constant buffer b1, uploaded by the presenting thread only when it changes (`Presenter::SetNightStrength`, any thread, never presents); an unbound buffer reads 0, so a failed one shows the picture unchanged. Auto (`AutoNightMode`, `core/night_mode.h`): the Source summarises about every 15th frame's luma on its coarse grid (`Source::SceneLuma`, a few microseconds); every 250 ms while Playing the FeedKeeper smooths it (time constant 2.5 s, so flashes and headlights do not pump the picture) and maps it to a strength: full at a mean luma of 45 or less, none at 95 or more, even in between. Those three numbers are the ones to tune. With no picture the strength is held. Logs `Night mode: auto strength S (scene luma L)` when it moves by 0.1 or reaches 0 or 1. Changing it never presents by itself: the feedback line (`Night mode low`) presents once, with the new look. Logs `Menu: Night mode ...`. The same curve is checked on the CPU in `tests/night_mode_test.cpp` (never darker, never out of order, never above 1). Started as the `prototype/shadow-boost` experiment (Shadow Boost on N).

## Colour range

Press R or select View > Colour range to step auto, limited, full (remembered as `colour_range=auto|limited|full`; missing or unknown means auto). Auto converts the Feed as the Capture Card's mode says (limited when it says nothing). Limited or full replaces only the range the card stated (`WithRange`, `core/colour.h`), for a card or console that sends one and labels it the other: a washed-out grey-black picture wants limited, crushed blacks want full. The Presenter (`SetColourRange`, any thread, atomic) rebuilds the conversion constants on the next frame converted; no present of its own, so on a still picture it shows with the next Unique Frame. Logs `Menu: Colour range ...` and the Presenter's `range used` on its picture line.

## Key list

H or F1 shows the key list over the picture, centred (`TextPlace::Help`, drawn last, `KeyHelpText` in `core/menu_model.h`: the same lines as Help > Hotkeys); H, F1 or Esc hides it (Esc then does not leave fullscreen; the next Esc does). Left-aligned, a tab stop six detail-font ems wide for the key column. Sized to fit the smallest window (`SizeText`, checked in `tests/video_area_text_test.cpp`). Never saved. Showing or hiding it presents once, like a feedback line. Logs `Key: key list shown|hidden`.

## Lossless Scaling

Use in-app Frame Generation or Lossless Scaling, never both: Lossless Scaling would count Generated Frames as real ones. The user's one-time setup guide is `docs/lossless-scaling-setup.md`, written in the user's vertical style (very short lines, one idea per line, no bullets); keep that style when editing it. What keeps the window a good target (ticket 10): the title is set once to exactly "GamePlayer" and never changed (no `SetWindowText`; debug numbers go to the log or the FPS counter, never the title); the exe is `GamePlayer.exe`; DXGI Alt+Enter is disabled and nothing calls `SetFullscreenState`; the Presenter presents only for a new Unique Frame, a resize, a device rebuild, or a text that appears or ends (the FPS counter never presents; the Frame rate override "60 fps (every frame)" passes Repeated Frames on too, so Lossless Scaling then sees 60); fullscreen uses `HWND_TOP`, never topmost, and hides the cursor after 2 s.

## Module layout

The pipeline has three stages (ADR 0002): Source, Processor, Presenter. Names follow `GLOSSARY.md`.

- `src/core/`: pure logic with no window, device or GPU. All of it is unit-tested in `tests/`.
  - `frame.h`: the `Frame` that travels through the pipeline (pixels, format, colour description, arrival time) and the pool that recycles frame buffers.
  - `source.h`: the `Source` interface. Capture sits behind it so another implementation could replace Media Foundation.
  - `processor.h`: the `Processor` interface (one frame in, zero or more timed frames out) and the pass-through Processor.
  - `unique_frames.h`: the Processor in use. Drops Repeated Frames (exact compare; near-duplicate tolerance `kNearDuplicateTolerance`, the one number to tune, default 0 = exact only), the Auto / 30 / 60 override, Signal Rate and Game Rate, the last three Unique Frames, the FPS counter text.
  - `capture_choice.h`: which capture device and which mode to use, with no configuration, and the resolutions offered in the menu (uncompressed, at most 60 fps, no MJPEG twins).
  - `viewer_settings.h`: every menu override in one structure with its defaults. `menu_model.h`: the menu's labels, check marks, Hotkeys and About texts.
  - `settings_file.h`: the remembered settings as text and back (every damage gives defaults), and when to save (`SettingsSaveTiming`).
  - `colour.h`: the YUV to RGB numbers for a frame's colour range and matrix.
  - `generation_notice.h`: typed generation failure/fallback outcomes and an owned thread-safe mailbox for the window.
  - `presentation_info.h`: actual generation/upscale state and rolling successful-present counts for Shown; no refresh cap.
  - `night_mode.h`: Night mode's choice (off, low, high), its strength and its word in the settings file.
  - `picture_fit.h`: where the 16:9 picture goes inside the Video Area, and whether Sharp Upscale is used for it.
  - `frame_schedule.h`: the timed sequence for one Unique Frame (when each Generated Frame and the Unique Frame are due, early drops, late skips, when not to generate).
  - `target_schedule.h`: Target (ADR 0004): which ladder frame each vsync shows, the nearest in time; never backwards; every Unique Frame itself shown; real frames only when the rate in use is not above the Game Rate (`RealFramesOnly`). Uses `FrameSchedule`'s arrival rules, nothing else of it.
  - `ladder_depth.h`: Target's x4 / x8 choice with hysteresis, the third FRC stage's restart and all-or-fall-back rules, and the latest start of a ladder.
  - `target_rate.h`: the Target Rate (ticket 03): the presets, the Custom box's check and starting number (ticket 04), the rate in use, `PresentPacer` (even spreading below the refresh), the real-frames-only rule, the uneven notice.
  - `vsync_clock.h`: Target's vblank times from the swap chain's frame statistics: the display time of the next present, the measured period, missed vsyncs, late presents.
  - `window_shape.h`: the window rectangle while an edge or corner is dragged, so the windowed Video Area stays exactly 16:9 (WM_SIZING), and whether a remembered one may be restored.
  - `monitor_choice.h`, `cursor_idle.h`, `stay_awake.h`: which monitor fullscreen covers, when the cursor hides, when to keep the PC awake.
  - `video_area_state.h`: the Video Area states (Loading, No Capture Card, Card busy, No signal, Playing, Error), their messages, and when to restart picture and sound.
  - `video_area_text.h`: text shown in the Video Area (headline and smaller detail line, three places) and its sizes for a given window.
  - `luma_summary.h`: brightness of a frame on a coarse grid, logged for no-signal investigation only.
  - `latest_slot.h`: the single-frame hand-off between threads (a newer frame replaces an unshown one).
  - `sound_playout.h`: everything between sound capture and sound output: priming to the target fill (`kTargetFillSeconds`, the one number to tune), underrun and overrun recovery. Built from `sound_ring.h` (the buffer), `drift_correction.h` (holds the fill at its target by a tiny playback rate change), `resampler.h` (rate conversion) and `pcm.h` (sample format conversion). `capture_choice.h` also picks the audio capture endpoint. The playout also applies the gain (volume, mute) and the Audio Delay (extra target fill), both without clicks; every start of the sound fades in from silence to the gain set. An Audio Delay change keeps the clock difference drift correction has learnt.
  - `audio_controls.h`: what Up, Down, M, J, K do to volume, mute and Audio Delay, and the confirmation line for each.
  - `shown_texts.h`: the texts the Video Area shows per place, when the brief ones (that line) end, and whether a change needs a present; the Presenter keeps one and passes the clock in.
- `src/platform/`: the parts that talk to Windows. Not unit-tested; checked by review, the debug log and the user's eyes.
  - `mf_source.*`: the Media Foundation Source Reader implementation of `Source`.
  - `presenter.*`: the `Presenter`. Owns the Direct3D 11 device, the flip-model swap chain, the shaders and its own presenting thread. Recreates the device if it is lost. Runs a `FrameGenerator`'s timed sequences when one is set (or, in Target, presents paced over the vsyncs), and the FSR 1 Sharp Upscale passes (`sharp_upscale_shader.h`). Text in the Video Area: `ShowText(place, text, durationMs)` from any thread (durationMs > 0 for brief feedback); `ShowPicture(false)` while a state message shows.
  - `frame_generator.*`: the `FrameGenerator` interface the Presenter asks for Generated Frames, and the developer-only repeat generator (`--frames-per-unique`).
  - `amf_generator.*`: Frame Generation 2x / 4x (and Target's x8 ladder, a third FRC) with AMD AMF FRC; starts each driver session on its own worker thread.
  - `amf_upscaler.*`: Sharp Upscale with AMD VideoSR (AMF HQScaler), FSR 1 until ready or after a failure.
  - `gpu_priority.*`: the process's GPU scheduling class raised to High.
  - `night_mode_shader.h`: Night mode's curve, prepended to every Presenter shader.
  - `sharp_upscale_shader.h`: the FSR 1 EASU and RCAS shaders (AMD, MIT; notice in the file and `third_party/fsr1/LICENSE.txt`).
  - `text_overlay.*`: draws those texts with Direct2D and DirectWrite into the back buffer.
  - `feed_keeper.*`: runs Source, Processor, Presenter and sound; follows `video_area_state.h`, restarts picture and sound together, reacts to device notifications and resume from sleep.
  - `sound.*`: the Feed sound. WASAPI shared mode, event-driven, capture from the card's endpoint and render to the Windows default output, following changes to that default. Volume, mute and Audio Delay are plain get / set values here.
  - `feedback.*`: shows the confirmation line through `Presenter::ShowText(TextPlace::Top, ..., 1500)`. The Presenter presents by itself when a text appears or ends, so it shows and clears on time even with a static, black or absent picture.
  - `fullscreen.*`: borderless fullscreen (F11, Esc), the hiding cursor (after 2 s still; windowed only over the Video Area of the active window, never during a menu, move or resize), monitor changes. Window chrome (menu bar and topmost flag included) is hidden and restored in one place, `ShowChrome`.
  - `menu_bar.*`: the native menu bar, refreshed from `menu_model.h` each time a menu opens.
  - `target_rate_box.*`: the modal Custom Target rate box (ticket 04).
  - `keep_awake.*`: no system or display sleep while a Feed plays (the Playing state only). Holds a power request (`powercfg /requests`, elevated, lists "GamePlayer: a Feed is playing") and the window thread's execution state, and resets the idle timers each second. Logs take, release (with reason), a minute-by-minute "still held", and every display on / off / dimmed.
  - `settings_store.*`: the settings file's place (`SHGetKnownFolderPath`), reading it, and writing it safely.
  - `single_instance.*`: a second launch brings the running window forward once it is shown and exits (waits up to 10 s; if the running copy was closing, this one starts).
  - `log.*`: the debug log.
- `src/app/main.cpp`: the window. Opens with a 16:9 Video Area (1280x720, smaller if the monitor is), minimum 480x270 at 100% scaling, and keeps 16:9 while dragged and when moved to a monitor with other scaling (`WM_DPICHANGED`). Maximised, fullscreen, snaps and programmatic sizes may give other shapes; the picture then keeps its shape with black bars.
- `third_party/doctest/`: the vendored test framework (one header).
- `third_party/amf/`: the AMF SDK headers Frame Generation compiles against (MIT).
- `third_party/fsr1/`: the licence of the FSR 1 code in `sharp_upscale_shader.h` (MIT).
- `prototype/`: the throwaway prototype from ticket 01. Reference only; not part of the app.

Threads: the window's thread runs the message loop; a Media Foundation thread delivers frames and runs the Processor; the Presenter's thread uploads, converts and presents. The Source's thread never waits for the GPU. Frame Generation and AMD VideoSR each start each AMF driver session on a short-lived, detached worker thread; it holds its own device reference and only sets a flag the Presenter reads when done. Sound has three more: capture and render (MMCSS "Pro Audio"), and a control thread that re-opens the output and writes the sound log lines.

Testing policy: unit tests for pure logic, code review for the rest, and the user checks picture and sound by hand.
