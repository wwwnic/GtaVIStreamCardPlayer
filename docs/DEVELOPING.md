# Developing GamePlayer

Needs Visual Studio Build Tools 2022 with the C++ workload (MSVC, Windows SDK, and the bundled CMake and Ninja). Nothing has to be on PATH; the scripts find the tools themselves.

## Build

    build.bat

Configures with CMake (Ninja, MSVC, RelWithDebInfo) and builds everything into `build\`. The app is `build\GamePlayer.exe`, a single executable with the C runtime linked in.

## Run the unit tests

    test.bat

Builds the test program and runs it (`build\gameplayer_tests.exe`, doctest). It exits non-zero if a test fails.

## Run

    build\GamePlayer.exe

F11 toggles borderless fullscreen; Esc leaves it. Up / Down change the volume, M mutes, J / K move the sound 50 ms earlier / later (Audio Delay, 0-500 ms); each shows a short line centred at the top for 1.5 s (a held key at a limit repeats nothing on screen; only the time restarts). F (or View > FPS counter) toggles the FPS counter top-left (with Frame Generation off, the presented rate, e.g. "30 FPS": the Game Rate on Auto, the Frame rate override's rate otherwise; blank for the first two seconds after a start or Feed restart, until the rate window is full; hidden while a state message such as Loading or No signal shows; the Signal Rate is in Help > About and the log; off on a fresh install, then remembered; drawn only into frames presented anyway, so it never adds a present and freezes on a still picture). `--rate auto|30|60` sets the Game Rate override, `--tolerance X` the near-duplicate tolerance (e.g. 0.005, at most 0.05), for one run (neither is saved). Once a second the log has a `Frames:` line: arrived, unique, repeats caught exactly and by the tolerance, presented, dropped, the Game Rate (detected), presented rate and Signal Rate, the largest near-repeat share and the closest Unique Frames (under 1% of words differing: a sign repeats are not bit-identical), the compare time before and after presenting, and the FPS counter text (or `warming up`, `off`). With Frame Generation running the counter has two equally sized lines, `Game 30` and `Shown 120`. During generation Game measures successful real endpoint presents (a superseded or failed endpoint is excluded), while off-mode retains the existing Processor-emitted rate. Shown measures all successful DXGI presents, including Generated Frames and repaints, over the last two seconds without a monitor cap. Starting, failed and unavailable generation retain the one-line counter. Help > About labels the override rate `Game:` during generation and shows measured total presents as `Shown:`; with generation off it keeps the old `Shown:` override line. It also reports the actual Generation Factor (or off, with the availability/startup reason), plus actual Sharp Upscale usage and Feed -> shown sizes. Driver failure and 4x fallback reasons reach About through a typed, owned notification mailbox; stale requests are discarded and no window message owns a raw pointer. The Presenter publishes these actual states under its statistics mutex; the FPS counter still never wakes it. Only one copy runs: while one is open, starting another just brings it forward (so a smoke run does nothing while the user's copy is open).

The menu bar (windowed only, hidden in fullscreen) overrides the automatic choices: Capture Card, Resolution, Frame rate, the audio values, Fullscreen, Always on top, V-sync (off by default), FPS counter. Two Capture Cards of the same name are numbered and told apart by their identifier. A chosen resolution that does not start, or that the card does not offer, gives way to the default mode for that run, with a short line saying so. Each choice logs a `Menu:` line; `Menu: open` / `closed` bracket an open menu.

Remembered settings (ticket 09): the menu choices, volume, mute, Audio Delay and the windowed position, size and maximised state are kept in `%APPDATA%\GamePlayer\settings.ini` (key=value, `version=1`; delete it for the defaults), and the FPS counter. Never fullscreen: the app always opens windowed, at the position it had before fullscreen. Saved about two seconds after a change settles and at exit, through a temporary file renamed over the old one. Anything missing or invalid is the default for that value; the window reopens at the size it had (a snapped one too, with black bars); a remembered position not fully on a connected monitor gives the default size on the primary monitor, not maximised. A save that fails is tried again after 30 s, on the next change, and at exit. The Capture Card is found by its symbolic link, then its name, else the automatic choice (the preference is kept). `--settings PATH` uses another file: smoke runs should, so the user's own file is left alone. The log has `Settings:` lines (what was loaded, each save) and `Window: remembered position ...`.

`--run N` closes the app by itself after N seconds, for unattended smoke runs. Each run rewrites `GamePlayer.log` beside the executable: the capture devices found, every mode the card offers, the chosen device and mode, the colour range and matrix read from that mode, then frame counts and the arrival-to-present time (once a second for ten seconds, then once a minute). For sound: every audio capture endpoint, the chosen one, both endpoints' formats, periods and buffers, the buffer target, then (same rhythm) the fill, drift correction rate, underruns and overruns. Video Area: every state change (`Video Area: Loading -> Playing`), and once a second a `Signal:` line with every value no-signal detection could use (frames, stream ticks, type changes, discontinuities, luma of the latest frame, sound frames, silent frames, peak). Retries log their details only when the device list changed. Each audio key logs the new volume, mute, Audio Delay and buffer target.

Press G or choose View > Frame generation to cycle through off, 2x, 4x and Target. The line says `Frame generation Target (144)` with the rate in use. The settings file remembers the choice as `frameGeneration=off`, `2x`, `4x` or `target`. Missing and unrecognised values select off. V-sync is unavailable while generating. With generation off, the Lossless Scaling present rules below apply.

Target (ADR 0004) shows one frame per refresh of the monitor the window is on, with V-sync on and no tearing. The rate in use is that monitor's refresh (`EnumDisplaySettings`), read again once a second, so it follows the window to another monitor. The V-sync item shows on and greyed out in Target; the user's own setting is not changed or saved and applies again after Target. Target runs the 4x generator (the 2x frames if the second FRC failed; Target stays on). The Presenter then skips the timed sequences: it waits on the swap chain's waitable object (once per vsync, max frame latency 1) and presents with sync interval 1 every time. A new Unique Frame is converted and generated as soon as it arrives, not at the vsync. For each vsync the pure `TargetSchedule` picks the ladder frame (first quarter, middle, last quarter, the Unique Frame) nearest in time to that vsync's display time, or none (the previous frame again). The ladder's times are those 4x would use: the first frame due when the ladder is ready, plus one refresh (a present is displayed at the next vblank), the others a quarter interval apart. It never goes backwards and never shows an older Unique Frame's frames after a newer one began. When the rate in use is not above the Game Rate, real frames only. The vblank times come from `IDXGISwapChain::GetFrameStatistics` after each present (`VsyncClock`). The vblank period is measured over 64 vblanks or more, else the monitor's nominal one. Missed vsyncs are the vblanks that showed no new present. Seen on the user's PC: borderless/windowed, 144 presents per second, 0 missed, period 6.946 ms. On the 59 Hz second monitor the swap chain still accepted 144 presents per second and its statistics report 144 Hz vblanks, so Target follows that measured cadence. Once a second the log has a `Target:` line: the rate in use, vsyncs, presents, Generated Frames and Unique Frames shown new, repeats, missed vsyncs, ladder depth (`x8`, `x4`, `x2`, `real frames only`), Unique Frames (and how many never had their own picture shown), the period (measured or nominal), the worst generation time, and where the vsync times came from. At a forced 30 fps it reads about 144 vsyncs and presents, 90 Generated, 30 Unique, 24 repeats. The arrival-to-present time in the `Stats:` line is about 29 ms (4x: about 25 ms). The FPS counter keeps its two lines: Shown is all presents (about 144), Game the real ones.

`platform/amf_generator.cpp` loads the AMD driver's AMF runtime from the Windows system directory. A worker creates FRC on the Presenter's Direct3D 11 device at the Feed size. It holds its own device reference until setup finishes, so the Presenter can show real frames, switch off, rebuild or stop during setup. FRC uses interpolated-only mode, high quality, fallback blending and no future frame. The Presenter copies each BGRA input into a four-texture ring. After submitting N it polls for about 2 ms, discarding outputs whose timestamp differs from N. A matching intermediate frame precedes N by half the Unique Frame interval. When none is ready, N is shown alone. The Presenter draws its texts after generation. A runtime failure disables generation for the session and preserves the saved choice. During asynchronous startup the Presenter retains the latest real BGRA picture in its own texture, then primes both stages from that picture on the first ready call. The worker never uses the immediate context for this priming. Its driver setup (`InitDX11`, FRC `Init`) does run on the shared device with multithread protection on; that makes each context call safe but does not keep a Presenter pass whole, so a driver that changes context state during setup could disturb one frame. Not seen so far. A size/device change still needs new asynchronous driver setup: its completion time is unbounded, so the ticket 03 two-Unique-Frame target cannot be guaranteed across such a change. Once setup is ready and the incoming interval is suitable, the retained previous picture permits 4x on that first ready call instead of wasting another input. A pause/restart with an existing ready session still re-primes within two Unique Frames. Startup logs report elapsed setup time, real input count and the first ready output count.

The x8 ladder (Target only, ticket 02). When the Game Rate is low for the rate in use, Target asks for seven Generated Frames per Unique Frame instead of three: the eighths 1/8, 3/8, 5/8, 7/8 between the quarters. The pure `LadderDepth` (`core/ladder_depth.h`) chooses x4 or x8 per Unique Frame from the Game Rate over about the last second (at least half a second measured; until then, and after `Reset` when generation stops, x4) and the measured refresh: x8 above 2.8 refreshes per Unique Frame, x4 below 2.5, in between it keeps what it had (at 144: about 51 fps and below x8, 58 and above x4). A pause or Feed restart keeps the depth and measures again. The Presenter passes it as `FrameGenerator::Input::eighths`; 2x and 4x never set it. In Target (with the second FRC) `MakeAmfGenerator(four, onFailure, eighths=true)` also starts a third FRC on the worker; it is fed only while x8 is wanted, with the quarter stream (first quarter, middle, last quarter, N; sequence numbers N x 4 - 3 ... N x 4, eight input copies). Same rules as the second stage (`ThirdStageStep`): an output is used only with the number just submitted; if it was idle, N's quarters are missing, or the earlier frame was forgotten, its history is flushed and restarts at N, and that Unique Frame uses x4. All or fall back (`ReadyLadderFrames`): seven only with all four eighths, else the quarters' count; never a partial x8. `Generated(i)` with seven: eighths at even places, Q1, M, Q3 at 1, 3, 5. If the third FRC cannot be created or fails, the generator logs `FrameGen: third FRC unavailable (reason), Target uses the x4 ladder`, Target stays on x4 and the window shows `Frame generation Target (x4 ladder only)` once (`GenerationOutcome::FallbackToQuadruple`; the reason goes to the log only, not About); the next generator in the session is made without a third FRC. A second-stage failure also ends x8. Generation runs on the presenting thread and x8's seven FRC calls take about 5.3 ms. Taken at once (as x4 does), they often straddled a vblank (6-18 missed vsyncs a second). So while the depth is x8 a new Unique Frame waits in the slot for the vsync: that pass presents first, then takes, converts and generates, which fits before the next vblank. Its ladder would then end after the next Unique Frame is taken, and the Unique Frame's own picture would almost never be shown: `LadderStartTicks` starts an x8 ladder at most a refresh and 1.25 eighths after the Unique Frame's arrival (30 fps at 144: about 12.1 ms), counted from the arrival so the steps stay evenly spaced from ladder to ladder; the Unique Frame is then shown at the latest at the vsync that takes the next one; a ladder's first eighth may be passed over. x4 and 2x keep ticket 01's timing exactly (a cap like this would also show more of x4's Unique Frames at 60 fps: seen once, not adopted). The `Target:` line adds `(depth x8, Game Rate 30.0)`; a `Target: ladder depth x8 (...)` line logs each change. `FrameGen:` adds `eighth frames N (x8 wanted, made, x8 CPU average / worst)`, the time of the Unique Frames that got the whole x8 ladder. Seen on the user's PC at a forced 30 (60 s each): 720p and 1080p alike, 210 Generated Frames made per second, 144 presents, 0 missed vsyncs, 108-111 Generated and 30 Unique Frames shown, 3-7 repeats, at most 1 Unique Frame not shown per minute; x8 generation CPU 5.3 ms average (720p 5.31, 1080p 5.26), worst second 8.9 / 9.7 ms; arrival-to-present about 33-34 ms (x4: about 29). At a forced 60: x4, never x8, one depth line per run at 30 (no flipping).

At 4x a second FRC processes the doubled stream. It receives the middle frame and then real frame N, each with its own timestamp. Both matching quarter frames must arrive to show first quarter, middle, last quarter and N, each a quarter interval apart. A missing quarter leaves only the middle and N. After missing a middle or a discontinuity, the second FRC starts its history at N. A second-stage failure leaves 2x running and updates the feedback and menu. The Viewer applies no monitor refresh cap.

`FrameGen:` logs the start result and, during playback, the factor, Generated Frames made, Unique Frame intervals attempted, quarter frames used, successful presents, discarded late outputs, and average and worst generation time per attempt on the presenting thread. GPU time is unmeasured.

The explicit `60 fps (every frame)` override deliberately passes Repeated Frames to the Presenter and FRC too, preserving the existing user choice. Frame Generation follows that real-input cadence; Auto remains the mode that drops Repeated Frames before generating. This override is covered by the Processor tests and does not silently turn back into Auto.

The developer-only command-line switch `--frames-per-unique 2` or `--frames-per-unique 4` repeats each picture at equal intervals. The presenting thread asks the GPU-side `FrameGenerator` for intermediate pictures and draws the overlays onto each output. The pure `FrameSchedule` uses the last two Unique Frame arrival times for spacing and anchors all deadlines to the first present. A high-resolution waitable timer wakes the presenting thread. Text, resize and menu wake-ups recheck the same deadline. A new arrival supersedes an unfinished sequence. Starts, Feed restarts, device rebuilds, picture-size changes and unsuitable arrival intervals show one frame immediately. During timed sequences the Presenter uses unsynchronised presents. The once-per-second `Timed frames` log counts Unique Frames, successful presents, early drops and late skips, and records the worst lateness and Present call duration. The switch is never saved.

## Sharp Upscale

Press U or select View > Sharp upscale to toggle the remembered choice (off on first use).
Every actual toggle logs `Menu: Sharp upscale on/off`, even at native size where FSR 1 is unused.
For an enlarged Feed the Presenter runs FSR 1 EASU directly from each finished picture
to a texture matching the fitted picture rectangle. RCAS sharpens that texture pixel for
pixel at 0.2 stops below maximum. Both passes use the same display-encoded RGB as the
plain stretch. Generated Frames follow the same path and the text overlay is drawn last.
Native-size and smaller pictures use the smooth path. The optional D3D11 shaders require
no AMF runtime. An `Upscale: FSR 1 on/off` transition logs the Feed and shown sizes.
Compilation or resource failure logs the reason and falls back to smooth stretching.

## Lossless Scaling

Use in-app Frame Generation or Lossless Scaling, never both: Lossless Scaling would count Generated Frames as real ones. The user's one-time setup guide is `docs/lossless-scaling-setup.md`, written in the user's vertical style (very short lines, one idea per line, no bullets); keep that style when editing it. What keeps the window a good target (ticket 10): the title is set once to exactly "GamePlayer" and never changed (no `SetWindowText`; debug numbers go to the log or the FPS counter, never the title); the exe is `GamePlayer.exe`; DXGI Alt+Enter is disabled and nothing calls `SetFullscreenState`; the Presenter presents only for a new Unique Frame, a resize, a device rebuild, or a text that appears or ends (the FPS counter never presents; the Frame rate override "60 fps (every frame)" passes Repeated Frames on too, so Lossless Scaling then sees 60); fullscreen uses `HWND_TOP`, never topmost, and hides the cursor after 2 s.

## Module layout

The pipeline has three stages (ADR 0002): Source, Processor, Presenter. Names follow `GLOSSARY.md`.

- `src/core/`: pure logic with no window, device or GPU. All of it is unit-tested in `tests/`.
  - `frame.h`: the `Frame` that travels through the pipeline (pixels, format, colour description, arrival time) and the pool that recycles frame buffers.
  - `source.h`: the `Source` interface. Capture sits behind it so another implementation could replace Media Foundation.
  - `processor.h`: the `Processor` interface (one frame in, zero or more timed frames out) and the pass-through Processor.
  - `unique_frames.h`: the Processor in use. Drops Repeated Frames (exact compare; near-duplicate tolerance `kNearDuplicateTolerance`, the one number to tune, default 0 = exact only), the Auto / 30 / 60 override, Signal Rate and Game Rate, the last three Unique Frames, the FPS counter text.
  - `capture_choice.h`: which capture device and which mode to use, with no configuration, and the resolutions offered in the menu (uncompressed, at most 60 fps, no MJPEG twins).
  - `viewer_settings.h`: every menu override in one structure with its defaults. `menu_model.h`: the menu's labels, check marks, Hotkeys and About texts.
  - `settings_file.h`: the remembered settings as text and back (every damage gives defaults), and when to save (`SettingsSaveTiming`).
  - `colour.h`: the YUV to RGB numbers for a frame's colour range and matrix.
  - `generation_notice.h`: typed generation failure/fallback outcomes and an owned thread-safe mailbox for the window.
  - `presentation_info.h`: actual generation/upscale state and rolling successful-present counts for Shown; no refresh cap.
  - `picture_fit.h`: where the 16:9 picture goes inside the Video Area, and whether Sharp Upscale is used for it.
  - `frame_schedule.h`: the timed sequence for one Unique Frame (when each Generated Frame and the Unique Frame are due, early drops, late skips, when not to generate).
  - `target_schedule.h`: Target (ADR 0004): which ladder frame each vsync shows, the nearest in time; never backwards; real frames only when the rate in use is not above the Game Rate. Uses `FrameSchedule`'s arrival rules, nothing else of it.
  - `ladder_depth.h`: Target's x4 / x8 choice with hysteresis, the third FRC stage's restart and all-or-fall-back rules, and the latest start of a ladder.
  - `vsync_clock.h`: Target's vblank times from the swap chain's frame statistics: the display time of the next present, the measured period, missed vsyncs.
  - `window_shape.h`: the window rectangle while an edge or corner is dragged, so the windowed Video Area stays exactly 16:9 (WM_SIZING), and whether a remembered one may be restored.
  - `monitor_choice.h`, `cursor_idle.h`, `stay_awake.h`: which monitor fullscreen covers, when the cursor hides, when to keep the PC awake.
  - `video_area_state.h`: the Video Area states (Loading, No Capture Card, Card busy, No signal, Playing, Error), their messages, and when to restart picture and sound.
  - `video_area_text.h`: text shown in the Video Area (headline and smaller detail line, three places) and its sizes for a given window.
  - `luma_summary.h`: brightness of a frame on a coarse grid, logged for no-signal investigation only.
  - `latest_slot.h`: the single-frame hand-off between threads (a newer frame replaces an unshown one).
  - `sound_playout.h`: everything between sound capture and sound output: priming to the target fill (`kTargetFillSeconds`, the one number to tune), underrun and overrun recovery. Built from `sound_ring.h` (the buffer), `drift_correction.h` (holds the fill at its target by a tiny playback rate change), `resampler.h` (rate conversion) and `pcm.h` (sample format conversion). `capture_choice.h` also picks the audio capture endpoint. The playout also applies the gain (volume, mute) and the Audio Delay (extra target fill), both without clicks; every start of the sound fades in from silence to the gain set. An Audio Delay change keeps the clock difference drift correction has learnt.
  - `audio_controls.h`: what Up, Down, M, J, K do to volume, mute and Audio Delay, and the confirmation line for each.
  - `shown_texts.h`: the texts the Video Area shows per place, when the brief ones (that line) end, and whether a change needs a present; the Presenter keeps one and passes the clock in.
- `src/platform/`: the parts that talk to Windows. Not unit-tested; checked by review, the debug log and the user's eyes.
  - `mf_source.*`: the Media Foundation Source Reader implementation of `Source`.
  - `presenter.*`: the `Presenter`. Owns the Direct3D 11 device, the flip-model swap chain, the shaders and its own presenting thread. Recreates the device if it is lost. Runs a `FrameGenerator`'s timed sequences when one is set (or, in Target, one present per vsync), and the FSR 1 Sharp Upscale passes (`sharp_upscale_shader.h`). Text in the Video Area: `ShowText(place, text, durationMs)` from any thread (durationMs > 0 for brief feedback); `ShowPicture(false)` while a state message shows.
  - `frame_generator.*`: the `FrameGenerator` interface the Presenter asks for Generated Frames, and the developer-only repeat generator (`--frames-per-unique`).
  - `amf_generator.*`: Frame Generation 2x / 4x (and Target's x8 ladder, a third FRC) with AMD AMF FRC; starts each driver session on its own worker thread.
  - `sharp_upscale_shader.h`: the FSR 1 EASU and RCAS shaders (AMD, MIT; notice in the file and `third_party/fsr1/LICENSE.txt`).
  - `text_overlay.*`: draws those texts with Direct2D and DirectWrite into the back buffer.
  - `feed_keeper.*`: runs Source, Processor, Presenter and sound; follows `video_area_state.h`, restarts picture and sound together, reacts to device notifications and resume from sleep.
  - `sound.*`: the Feed sound. WASAPI shared mode, event-driven, capture from the card's endpoint and render to the Windows default output, following changes to that default. Volume, mute and Audio Delay are plain get / set values here.
  - `feedback.*`: shows the confirmation line through `Presenter::ShowText(TextPlace::Top, ..., 1500)`. The Presenter presents by itself when a text appears or ends, so it shows and clears on time even with a static, black or absent picture.
  - `fullscreen.*`: borderless fullscreen (F11, Esc), the hiding cursor (after 2 s still; windowed only over the Video Area of the active window, never during a menu, move or resize), monitor changes. Window chrome (menu bar and topmost flag included) is hidden and restored in one place, `ShowChrome`.
  - `menu_bar.*`: the native menu bar, refreshed from `menu_model.h` each time a menu opens.
  - `keep_awake.*`: no system or display sleep while a Feed plays (the Playing state only). Holds a power request (`powercfg /requests`, elevated, lists "GamePlayer: a Feed is playing") and the window thread's execution state, and resets the idle timers each second. Logs take, release (with reason), a minute-by-minute "still held", and every display on / off / dimmed.
  - `settings_store.*`: the settings file's place (`SHGetKnownFolderPath`), reading it, and writing it safely.
  - `single_instance.*`: a second launch brings the running window forward once it is shown and exits (waits up to 10 s; if the running copy was closing, this one starts).
  - `log.*`: the debug log.
- `src/app/main.cpp`: the window. Opens with a 16:9 Video Area (1280x720, smaller if the monitor is), minimum 480x270 at 100% scaling, and keeps 16:9 while dragged and when moved to a monitor with other scaling (`WM_DPICHANGED`). Maximised, fullscreen, snaps and programmatic sizes may give other shapes; the picture then keeps its shape with black bars.
- `third_party/doctest/`: the vendored test framework (one header).
- `third_party/amf/`: the AMF SDK headers Frame Generation compiles against (MIT).
- `third_party/fsr1/`: the licence of the FSR 1 code in `sharp_upscale_shader.h` (MIT).
- `prototype/`: the throwaway prototype from ticket 01. Reference only; not part of the app.

Threads: the window's thread runs the message loop; a Media Foundation thread delivers frames and runs the Processor; the Presenter's thread uploads, converts and presents. The Source's thread never waits for the GPU. Frame Generation starts each AMF driver session on a short-lived, detached worker thread; it holds its own device reference and only sets a flag the Presenter reads when done. Sound has three more: capture and render (MMCSS "Pro Audio"), and a control thread that re-opens the output and writes the sound log lines.

Testing policy: unit tests for pure logic, code review for the rest, and the user checks picture and sound by hand.
